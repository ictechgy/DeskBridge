# File transfer implementation and boundary

Knot speaks structured SFTP v3 over a child `/usr/bin/ssh -s ... sftp` process. SSH supplies maintained authentication, host verification and encrypted transport on LAN as well as Tailscale. There is no custom cryptography, HTTP file service or dependency on Sunshine's privileged process. SFTP is a separate credential and permission boundary from full remote desktop control; someone authorized to control the desktop can still use the desktop's own applications to reach that Windows account's files.

`SFTPConnectionConfiguration` requires a Windows address, dedicated local username, explicit private-key URL and independently verified Ed25519 **server** public key. It computes a SHA256 fingerprint and writes that exact pin to a new app-owned `known_hosts` file with private permissions. A stable host-key alias supports changing between LAN and Tailscale addresses without trusting a new endpoint. Unknown/changed keys fail closed. No network key scan is silently trusted.

The SSH process receives individual arguments, no shell. It ignores inherited SSH config using `-F /dev/null` and sets key-only `BatchMode`, `IdentitiesOnly`, strict host checks, app-owned known hosts, `/dev/null` global known hosts, no forwarding/PTY/proxy/control socket and bounded connection/keepalive timeouts. Only the selected identity is offered; an already unlocked matching key can be provided by the local SSH agent. Passphrases are not sent through command arguments and no GUI password/askpass subprocess is spawned. Filenames are binary SFTP strings, never batch commands, shell fragments or parsed `ls` text. Remote stderr is not persisted or surfaced as raw logs. A separate draining pipe inspects at most4096 bytes through a signature-sized rolling window and emits only fixed host-key/authentication/refused-port/network guidance for startup disconnects. It never emits complete diagnostic lines or changes cancellation/deadline/protocol failures into authentication errors.

The codec validates packet/string lengths, protocol version, response IDs, attribute flags and directory limits. Nonblocking pipe I/O has a monotonic 30-second deadline per complete packet; keepalive responses alone cannot keep a stalled SFTP subsystem waiting forever. Requests are serial with 64 KiB file chunks and a 128 GiB MVP file-size limit. This favors a small bounded implementation; high-latency SFTP throughput has not been optimized or benchmarked. Folder recursion, resumable transfers, server-side content hashing, preserved permissions and multi-file drag/drop are outside this first version.

Listings preserve UTF-8 filenames including spaces, brackets and punctuation. Names containing control/format scalars (including bidirectional overrides), path separators or colons, and entries whose full path exceeds 8192 UTF-8 bytes, are omitted from listings and cannot be used for transfers or navigation; safe sibling entries remain available. Counts describe displayed entries, and an empty display does not assert the directory has no files. Omitted names still count toward directory response limits. Unrepresentable UTF-8 fails the response closed. Upload names are normalized to canonical composed Unicode (NFC) before applying Windows filename rules; canonically equivalent Korean names remain readable without expanded decomposed-name length limits. Symlinks are displayed but transfers through them are blocked by component `LSTAT` checks and file-type checks. **These client checks cannot authorize a share or eliminate server-side path races.** Configure Windows `ForceCommand internal-sftp`, `ChrootDirectory`, a dedicated non-administrator account, strict NTFS ACLs and firewall restrictions as described in `host/windows/README.md`. Keep junctions/reparse points out of the share. The Windows jail and ACLs, not a client-entered folder path, enforce root confinement.

Uploads create a fresh UUID job directory and exclusively create a staging file. The staging basename is `.upload.part`, or `.upload-stage.part` when the original filename equals `.upload.part` ignoring case. Thus even original files named `.upload.part` or `.UPLOAD.PART` have a distinct staging path on Windows. The client acknowledges every write, verifies remote size, closes and issues a base-v3 rename to the canonically composed filename inside that new directory. It does not use the overwriting `posix-rename@openssh.com` extension and never writes directly over an existing named document. Downloads create an exclusive mode-0600 partial with `openat(O_EXCL|O_NOFOLLOW)`, then finalize using `renameatx_np(RENAME_EXCL)` in the same open directory; existing final files are retained. Size/mtime checks detect common source changes but are not a snapshot or a cryptographic content hash.

Progress callbacks report actual acknowledged upload bytes or locally written download bytes. Cancelling wakes a blocked pipe poll through a separate anonymous cancellation pipe, terminates that operation's SSH transport and requires reconnecting. Local partial files are removed; remote cleanup is best effort and a disconnected upload may retain `.upload.part` or `.upload-stage.part` in its UUID job directory. An operation cancelled before commit is not complete; a transfer already committed remains reported complete even if its subsequent listing fails or is cancelled. The UI must not report pre-commit cancellation as successful completion or offer broad automatic deletion. Revoking a client public key does not by itself close an already authenticated SSH session; close sessions/stop the dedicated service for immediate revocation.

Terminal transport, timeout, cancellation and protocol failures clear the file connection and require reconnecting. A local destination/permission error or ordinary remote SFTP status preserves a still-valid connection. Setup import previews any shared screen/file target change, and model-level guards reject import while files or streaming are active.

Offline session checks use an in-memory synthetic SFTP peer and newly created temporary files. They exercise pin/argv validation, binary codecs, exact UTF-8 names, short-read downloads, bidirectional data, staging-name collisions under Windows case-insensitive rename rules, exclusive finalization, symlink/traversal rejection, cancellation cleanup and protocol failures. Separate anonymous-pipe checks execute `SFTPPipeFramer`, the exact four-byte packet framing and nonblocking I/O implementation used by `SFTPSSHTransport`. They cover outgoing prefixes, fragmented headers/payloads, oversized/zero/truncated frames, EOF, short deterministic receive/send deadlines and cancellation of waiting reads/writes. Neither suite establishes a socket or launches SSH. A live Windows 11 Home integration check remains necessary for authentication, jail/ACL semantics, key rotation, interrupted uploads and sustained throughput before release.

Primary references: [SFTP v3 wire format](https://www.ietf.org/archive/id/draft-ietf-secsh-filexfer-02.txt), [OpenSSH host verification options](https://man.openbsd.org/ssh_config.5), [OpenSSH forwarding/ForceCommand behavior](https://man.openbsd.org/sshd_config.5), [why a network key scan is not verification](https://man.openbsd.org/ssh-keyscan.1). The IETF document is the historical v3 protocol draft, not a published RFC.

Selected uploads are opened nonblocking before regular-file validation, so a FIFO cannot hold the file queue waiting for a writer. Public-key companions and setup replies also use bounded ordinary-file reads. The Mac rechecks activity and selected identity after modal setup panels before writing or importing settings.

Mac downloads select a destination folder and retain the remote filename. Existing names are rejected without a Replace prompt. The destination name (including dangling symlinks) is checked before transfer, and the open exclusive partial file receives a `com.apple.quarantine` download marker before requesting remote file bytes; filesystems that cannot retain this marker fail the download and remove the partial file. No private endpoint/path is added to quarantine metadata.
